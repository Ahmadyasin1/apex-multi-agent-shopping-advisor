1. Project Overview

SECTION 01

APEX (Adaptive Product EXpert) is an Intelligent Shopping Advisor that solves a genuine consumer problem: making high-quality, unbiased product decisions in a market saturated with paid reviews, sponsored content, and conflicting opinions. Users can ask natural-language questions like "Best gaming laptop under $2,000 with RTX GPU" and receive structured, fact-based recommendations backed by transparent scoring.

Core Problem Solved
Traditional product search returns keyword-matched lists with no reasoning. APEX applies multi-dimensional analysis (price, performance, brand, durability, innovation) and Pareto optimality theory to surface only genuinely non-dominated product choices, with every recommendation fully explained and traceable to data.

The system is built around a LangGraph StateGraph with 8 specialized agents, a 51-product FAISS-indexed dataset, Google Gemini 2.0 Flash as the primary LLM, and a real-time WebSocket streaming backend. The luxury premium frontend provides an exceptional user experience with live pipeline visualization, interactive comparisons, and adaptive personalization.

2. System Architecture

SECTION 02

APEX follows a hierarchical multi-agent pipeline orchestrated by LangGraph. A single AgentState TypedDict object flows through every node, carrying all shared data. This design ensures agents are fully decoupled — each reads only what it needs and writes only its own outputs.

User Query (Natural Language) │ ▼ ┌──────────────────────────────────────────────────────────────────┐ │ LANGGRAPH STATEGRAPH │ │ │ │ ①Supervisor ──▶ ②Preference ──▶ ③Retrieval ──▶ ④Enrichment │ │ │ │ │ ┌── FAIL ◀──────┤ │ │ │ (retry ≤2) ▼ │ │ │ ⑤Comparison ──▶ ⑥Critique │ │ └──────────────────────────────┘ │ │ │ PASS │ │ ▼ │ │ ⑦Recommendation ──▶ ⑧Learning │ │ │ │ └──────────────────────────────────────────────────────── END ──── ┘ │ ▼ WebSocket JSON Stream → Frontend (real-time per-agent events)

Key Architectural Decisions

  • Linear pipeline with one conditional edge — keeps the graph simple and debuggable while enabling self-correction
  • Hard retry cap — Critique agent failure triggers maximum 2 re-attempts before forcing pass, preventing infinite loops
  • Streaming via workflow.stream() — each node completion fires a WebSocket event, enabling live UI updates
  • Deterministic scoring — Comparison and Enrichment agents use no LLM, eliminating hallucination from the scoring layer
  • Three-tier LLM fallback — Gemini 2.0 Flash → Ollama (local) → MockLLM ensures 100% uptime

3. Multi-Agent Design

SECTION 03

Each agent is a pure Python function (AgentState) → AgentState. LangGraph calls them in sequence, merging the returned state back into the graph. Agents are fully independent — they can be tested, replaced, or parallelized without modifying other agents.

Agent 1 — Supervisor (Master Orchestrator)

Entry point for every request. Classifies query complexity (simple vs complex) and selects the appropriate LLM tier to use for the rest of the pipeline. Also performs initial product category detection.

InputOutputLLM Used
Raw query stringcomplexity, selected_llm, categoryLocal (always — routing is cheap)

Agent 2 — Preference (Cognitive Intent Analyzer)

Transforms the query into a structured semantic model: budget range, feature keywords, and — most importantly — a 5-axis priority vector encoding what the user cares about most.

Priority Vector
Example: "I need a gaming laptop" → {price: 0.10, performance: 0.50, brand: 0.15, durability: 0.15, innovation: 0.10}
Example: "Cheap laptop for email" → {price: 0.50, performance: 0.15, brand: 0.10, durability: 0.15, innovation: 0.10}

Agent 3 — Retrieval (FAISS Semantic Search + RapidAPI)

Performs vector similarity search using all-MiniLM-L6-v2 SentenceTransformer embeddings against a pre-built FAISS L2 index of all 51 products. Results are post-filtered by budget and category. The RapidAPI client attempts to inject real-time product data as additional candidates.

query_embedding = encoder.encode("gaming laptop RTX")
distances, indices = faiss_index.search(query_embedding, top_k=15)
# → returns products sorted by semantic similarity

Agent 4 — Enrichment (Rule-Based Normalization)

No LLM — purely deterministic. Fills missing spec fields using price-based inference (e.g., a $2,500 laptop infers "32GB+ RAM"), generates fallback descriptions, assigns value tier labels, and infers ideal-for tags from feature keywords.

Agent 5 — Comparison (Pareto-Optimal 5D Scoring)

The core analytical engine. Computes a weighted overall score for each product and identifies Pareto-optimal choices. See Section 5 for the full scoring model.

Agent 6 — Critique (AI Quality Auditor)

Self-correction agent. Reviews the top-3 scored products and validates budget compliance, category match, and spec realism. If validation fails and retry count < 2, the pipeline loops back to Preference with critique feedback injected.

Agent 7 — Recommendation (LLM Advisory Report)

Uses the selected LLM (Gemini 2.0 Flash in production) to generate a structured markdown advisory report. The prompt provides complete product data (scores, specs, features, ideal_for) and instructs the model to produce per-product analysis with pros, cons, value verdict, and a strategic summary.

Agent 8 — Learning (Adaptive Memory)

Persists the session to data_layer/user_memory.json and updates a rolling preference average using exponential smoothing (α = 0.15). This enables the system to personalize future recommendations without requiring explicit user accounts.

FAISS Vector Database

Each product is embedded using the all-MiniLM-L6-v2 SentenceTransformer model into a 384-dimensional semantic vector. Embeddings are built from a rich text combining name, brand, category, description, features, and ideal_for fields. The FAISS L2 index enables sub-millisecond similarity search at inference time.

RapidAPI Integration (data_layer/rapidapi_client.py)

The Retrieval Agent attempts to enrich results with real-time product data via RapidAPI. The client implements timeout handling (15s), graceful degradation on failure, and safe key management through environment variables. On success, live external products are prepended to the local FAISS results as additional candidates.

5. Scoring & Pareto Optimality

SECTION 05

Weighted Multi-Dimensional Scoring Formula

overall_score = Σ dim_score[d] × priority_vector[d] for d ∈ {price, performance, brand, durability, innovation}

Dimension Scoring Rules

DimensionBase CalculationBonus Conditions
PriceInverse price relative to budget or category average+boost if price ≤ 50% of budget
Performancerating × 2.0 (capped at 10)+1.5 for RTX 4090/M3 Max; +0.8 for i7/RTX 4070
BrandTop-4 premium brand → 9.0; premium tier → 7.5; other → 5.0Category-specific PREMIUM_BRANDS lookup
Durabilityrating × 1.8+1.5 for MIL-SPEC/IP68/titanium; +0.8 for metal build
Innovation5.0 base+0.8 per innovation keyword (AI, OLED, LDAC, Neural Engine…)

Pareto Optimality Analysis

A product P is Pareto-optimal if no other product Q satisfies: Q scores ≥ P in all dimensions AND Q scores > P in at least one dimension. Pareto-optimal products are "honest" choices — improving one dimension necessarily requires sacrificing another.

This is implemented as an O(n²) pairwise dominance check across all returned products. Pareto-optimal products are flagged with is_pareto_optimal: true and highlighted in the UI.

Why Pareto Optimality?
Standard ranking algorithms collapse multi-dimensional quality into a single number, hiding important trade-offs. Pareto analysis preserves the full dimensionality — a student on a budget sees a different optimal set than a professional who cares only about durability.

6. LLM Integration Strategy

SECTION 06

APEX implements a three-tier LLM fallback chain to ensure 100% availability regardless of API quotas or local infrastructure:

TierModelUse CaseLatency
1. PrimaryGemini 2.0 FlashAll complex reasoning, recommendation generation3–15s
2. SecondaryOllama (llama3 local)When Gemini quota exhausted or offline10–40s
3. FallbackMockLLM (deterministic)Always available — parses product data from prompt<1s

The _QuotaAwareLLM wrapper in llm_factory.py catches RESOURCE_EXHAUSTED (HTTP 429) errors from Gemini and transparently switches the session to MockLLM, so the user always gets a response. Ollama availability is checked via a TCP socket probe before use.

The MockLLM (a Pydantic BaseChatModel subclass) is not simply a stub — it parses actual product names, prices, scores, and features from the recommendation prompt using regular expressions and generates structured, product-specific advisory text referencing real data points.

SECTION 07

The frontend (frontend/index.html, ~130KB) is a single-page application with a luxury dark aesthetic, Three.js particle field background, and real-time WebSocket integration. Key features:

  • Live Agent Pipeline Visualization — Each agent streams its status in real-time; a progress bar and per-agent timers are displayed

  • Budget Optimizer — Real-time slider ($100–$5,000) fetches top products via /api/budget-optimizer with 280ms debounce

  • Market Pulse Dashboard — Per-category intelligence: avg price, avg score, best-value product, value index
  • Price History Chart — 13-month simulated price trend per product with deal score (0–10) and buy advisory
  • Heat Map View — Toggle between product cards and a color-coded table (red→orange→green per score dimension)
  • Score Explainer — Click any score bar → API call → modal explaining exactly why that score was assigned
  • Radar & Scatter Charts — Chart.js radar (top-3 products) and bubble scatter (all 51 products by price vs score)
  • Voice Search — Web Speech API microphone integration
  • Comparison Table — Select up to 3 products for side-by-side spec and score comparison
  • Adaptive Follow-up — Suggested refinement queries appear after results; free-text follow-up combines with original context

9. Ethical & Practical Considerations

SECTION 09

Data Privacy

APEX stores zero personally identifiable information. The learning agent persists only aggregated preference signals (anonymous priority vector averages) and query text — no user accounts, no tracking cookies, no IP logging. The memory file (user_memory.json) is local-only and excluded from version control via .gitignore.

In a production multi-user deployment, this file would be replaced with a per-session Redis cache with automatic TTL expiry (e.g., 7 days), ensuring GDPR compliance by design.

Bias in Recommendations

The system has two potential bias sources that are acknowledged and partially mitigated:

Bias SourceDescriptionMitigation
Premium Brand WeightingPREMIUM_BRANDS dict gives higher brand scores to established manufacturersTransparent scoring — users can see exact dimension scores; Pareto analysis surfaces non-premium high-value products
Dataset Coverage51 products cannot represent the full market; missing brands will never appearRapidAPI real-time integration supplements with live external data; dataset is manually reviewed for balance
Training Data BiasGemini may have inherent biases from its training corpusLLM output is only used for narrative recommendation text; all factual scores are computed deterministically without LLM

Limitations of LLM-Based Systems

Known Limitations
  • Hallucination risk — Gemini may occasionally generate product specs that are inaccurate. APEX mitigates this by computing all scores deterministically; the LLM only generates advisory text, not factual data.
  • Context window — Very long product lists may be truncated in the LLM prompt. The system limits the recommendation prompt to top-5 products.
  • Prompt injection — Malicious user queries could attempt to manipulate LLM output. The preference extraction uses structured JSON output (Pydantic schema validation) rather than free text, reducing injection surface.
  • Latency — Gemini API calls add 3–15 seconds to the pipeline. MockLLM fallback ensures a fast response is always available.

Risks of Inaccurate or Outdated Product Data

Product data becomes stale as manufacturers release new versions, discontinue products, and adjust pricing. APEX addresses this through:

  • RapidAPI integration — live external product data supplements the static dataset
  • Price trend simulation — the /api/price-trend endpoint models historical price decay so users understand current pricing in context
  • Explicit data sourcing — recommendations include the product's source (local dataset vs. external API) so users know data freshness
  • Clear disclaimers — the UI notes that prices are indicative and users should verify before purchase

Scalability Considerations

  • Single-worker constraint — FAISS index is loaded into process memory; multi-worker deployments would require a shared vector store (Pinecone, Weaviate)
  • Pipeline latency — The 20–60s Gemini pipeline is best suited to asynchronous, non-concurrent usage; concurrent scaling requires a job queue (Celery + Redis)
  • Dataset expansion — The FAISS index can scale to thousands of products with no code changes; only the embedding rebuild time increases linearly
